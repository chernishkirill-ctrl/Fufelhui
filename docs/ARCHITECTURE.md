# Архитектура Telegram CRM агентства недвижимости

## 1. Общая схема

```
Риелтор/владелец (личка с ботом)  ──┐
Клиент (кнопка в канале → бот)    ──┼──► aiogram Dispatcher ──► middleware (сессия БД + роль по telegram_id)
Рабочий чат (кнопки в темах)      ──┘            │
                                                 ▼
                         handlers/ (UI, FSM, проверка прав)
                                                 │
                                                 ▼
          services/ (бизнес-логика)  ──►  database/ (SQLAlchemy 2.0 async → PostgreSQL)
                 │
                 ├── workchat_service   → темы «База», «Архив», «Заявки», «Сделки»
                 ├── publication_service → публичный канал + Telegraph
                 ├── parser_service      → parsers/ (OLX, DOM.RIA, универсальный)
                 └── scheduler           → ежедневные отчеты (APScheduler + /cron/*)
```

Цепочка данных: **объект → риелтор → публикация → заявка → просмотр → сделка → комиссия → статистика → отчет.**
Каждая сущность связана внешними ключами, все значимые события объекта пишутся в `property_history`.

## 3. Модель данных

| Таблица | Назначение | Ключевые связи |
|---|---|---|
| `users` | сотрудники: `telegram_id` (уникальный), username, имя, `role` (owner/admin/realtor), `status` (active/blocked/removed) | — |
| `invites` | одноразовые ссылки-приглашения риелторов (48 ч) | created_by → users, used_by → users |
| `properties` | объекты; внутренний код `OBJ-000125` = id; публичные поля + приватные (`owner_name`, `owner_phone`, `internal_comment`); служебные ID сообщений (канал, темы) | responsible_realtor_id, created_by_id → users |
| `property_history` | журнал: создание, изменения полей, статусы, архив, публикация, заявки, взятие клиента, сделки | property_id → properties (CASCADE), user_id → users |
| `leads` | заявки клиентов (клиенты не являются пользователями CRM) | property_id → properties, assigned_realtor_id → users |
| `deals` | сделки; `client_id` ссылается на заявку клиента | property_id, realtor_id, client_id → leads |
| `daily_reports` | отчеты; уникальность (realtor_id, report_date) — повторная отправка обновляет | realtor_id → users |
| `app_settings` | переключатели ⚙️, время отчетов, ID тем/чата, заданные из бота, токен Telegraph, маркеры рассылок | — |

Статусы объекта: `draft, active, published, reserved, sold, rented, inactive, archived`.
«Архивные» = `sold, rented, inactive, archived` — объект не удаляется, исчезает из активных списков, история сохраняется.

Статусы заявки: `new → assigned → in_progress → viewing_scheduled → viewing_done → closed | cancelled`.

Деньги — `Numeric(14,2)` + код валюты (USD/EUR/UAH); статистика суммирует отдельно по валютам.
Время хранится в UTC, отображается в `TIMEZONE`; периоды статистики считаются по локальным суткам.

## 4. Роли и права

| Действие | Владелец (OWNER_ID) | Риелтор (active) | Остальные |
|---|---|---|---|
| Пульт владельца, настройки, риелторы | ✅ | ❌ | ❌ |
| Смотреть общую базу объектов и историю | ✅ | ✅ | ❌ |
| Добавить / импортировать объект | ✅ | ✅ (становится ответственным) | ❌ |
| Изменить, статус, архив, фото | ✅ | только свои | ❌ |
| Назначить ответственного, удалить | ✅ | ❌ | ❌ |
| Публиковать в канал | ✅ | свои, если включено «Риелторы могут публиковать» | ❌ |
| Взять клиента | ✅ | ✅ (первый нажавший) | ❌ |
| Видеть контакты клиента | ✅ | только назначенный риелтор | ❌ |
| Зафиксировать сделку | ✅ (на любого риелтора) | только на себя | ❌ |
| Редактировать / отменить сделку | ✅ | ❌ | ❌ |
| Статистика | вся | только своя (+ рейтинг по сделкам, если разрешено) | ❌ |
| Запись на просмотр | ✅ | ✅ | ✅ |

Как это обеспечено:

* `DbSessionMiddleware` на каждом апдейте определяет `Actor` **по `from_user.id`**. Владелец — только если `id == OWNER_ID`
  (env); username обновляется лишь для отображения.
* Роутер владельца целиком закрыт фильтром `IsOwner`; роутер риелтора — `IsRealtor` (заблокированный = нет доступа).
* **Каждый** обработчик действия над объектом/заявкой/сделкой повторно вызывает функцию из `services/auth.py`
  с загруженной из БД сущностью — подделанный callback_data не дает прав. ID риелтора для «моей статистики» и
  «моих заявок» берется из `Actor`, а не из callback.
* Необработанные нажатия попадают в fallback: «Доступ запрещен.» для посторонних и для кнопок пульта владельца.

## 5. FSM (bot/handlers/states.py)

| Группа | Шаги |
|---|---|
| `PropertyAdd` | тип предложения → тип недвижимости → комнаты → площадь → этаж → цена → город → район → адрес → описание → контакт собственника → фото → подтверждение (с исправлением полей) |
| `PropertyImport` | URL → предпросмотр → [исправить поле] → сохранить / сохранить и опубликовать |
| `PropertyEdit` | значение поля; добавление фото |
| `PropertySearch` | запрос |
| `LeadBooking` (клиент) | имя (или из Telegram) → телефон (кнопка «Отправить мой номер» или пропуск) → время → комментарий → отправка |
| `LeadWork` | время просмотра; внутренняя заметка |
| `DealCreate` | объект → риелтор (владелец) → заявка клиента → тип → сумма → комиссия (сумма или %) → дата → комментарий → подтверждение |
| `DealEdit` | сумма / комиссия / дата / комментарий (владелец) |
| `ReportFill` | 6 числовых вопросов → комментарий → отправка |
| `StatsCustom`, `RealtorAdd`, `SettingsEdit` | период; Telegram ID; время отчетов |

Кнопки главного меню работают из любого состояния (сбрасывают диалог). `/cancel` и «✖️ Отмена» — всегда.
Хранилище FSM — в памяти: после перезапуска незавершенный диалог нужно начать заново (данные CRM в PostgreSQL не теряются).

права проверяются в личном чате по telegram_id, а в группе не появляются лишние сообщения.

## 7. Рабочий чат и Topics

* Бот пишет только в «База» (карточки новых объектов, обновляются при изменениях), «Архив», «Заявки»
  (`LEADS_TOPIC_ID`, иначе «База») и «Сделки». Тема «Чат» — для людей: middleware даже не открывает сессию БД
  на обычные сообщения группы.
* ID тем: из env (приоритет) или из бота — «⚙️ → Создать темы» (бот создает темы сам) либо `/settopic` внутри темы.
* При архивации карточка дублируется в «Архив», карточка в «База» помечается «Перенесен в архив»; при возврате — наоборот.

## 8. Импорт объекта

1. `extract_url` → `validate_url`: только http/https, стандартные порты, запрет приватных/loopback-адресов (SSRF), проверка каждого редиректа.
2. `fetch_html` (httpx, лимит 6 МБ, таймауты). 403/429/503 → понятное сообщение «сайт заблокировал…».
3. `pick_parser`: `OLXParser` → `DomRiaParser` → `GenericParser` (JSON-LD, OpenGraph, текстовые эвристики ru/uk).
4. `postprocess`: телефон собственника → приватное поле; из описания удаляются телефоны, ссылки, e-mail, @username,
   предложения с контактами/комиссией и имя собственника; определение района по словарю; валюта.
5. Предпросмотр → исправление полей → сохранение (`OBJ-XXXXXX`, история «создан (OLX)») → карточка в «База»
   → (опционально) публикация.

Новый источник: класс-наследник `BaseParser` в `bot/parsers/<site>.py` + добавить в `PARSERS`. Любое исключение парсера
перехватывается — бот отвечает «Не удалось автоматически получить данные по этой ссылке…».

## 9. Публикация

* Telegraph-страница (фото по URL + описание + характеристики, **без** внутренних данных). Токен из `TELEGRAPH_TOKEN`
  или создается автоматически и хранится в `app_settings`.
* Пост в канал: фото + подпись (тип, район, город, площадь, этаж, цена, короткое очищенное описание, `№ OBJ-…`, хэштеги)
  или альбом до 10 фото (переключатель). Кнопки: 📸 Подробнее (Telegraph), 📍 На карте, 📅 Записаться на просмотр (deep-link).
* «На карте»: координаты округляются до ~500 м, если не включено «Точная точка»; без координат — поиск по району и городу
  (адрес не раскрывается).
* Если Telegram не может скачать фото по URL (hotlink-защита), бот скачивает его сам и загружает файлом.
* Снятие с публикации удаляет пост(ы) из канала.

## 10. Заявки и «первый забрал клиента»

1. Клиент нажимает «📅 Записаться на просмотр» → бот → анкета → `create_lead` (антиспам: 1 открытая заявка на объект,
   ≤ 5 заявок в сутки) → **commit** → карточка в теме заявок (без контактов клиента) с кнопкой «🙋 Взять клиента».
2. Нажатие: одна SQL-команда

   ```sql
   UPDATE leads SET assigned_realtor_id = :me, status = 'assigned', assigned_at = now()
   WHERE id = :lead AND assigned_realtor_id IS NULL AND status = 'new'
   ```

   Успех = `rowcount == 1`. Затем commit, редактирование карточки в группе («Клиента взял(а) @…», кнопка убирается),
   контакты клиента — в личку победителю, уведомление владельцу.

### Проверка на гонки

* **PostgreSQL (READ COMMITTED)**: UPDATE берет row-lock. Вторая транзакция ждет, после коммита первой перечитывает строку
  и заново проверяет `WHERE` — `assigned_realtor_id` уже не NULL → 0 строк. Двойное назначение невозможно без
  SELECT … FOR UPDATE и без уровня SERIALIZABLE.
* Нет паттерна «прочитал → проверил в Python → записал» (он и дает гонки).
* Коммит выполняется **до** сетевых вызовов Telegram: сбой сети не откатывает назначение, а повторное нажатие получит
  понятный ответ.
* Проигравший получает «Заявку уже забрал другой риелтор»; если карточку по какой-то причине не удалось обновить,
  она обновляется при этом нажатии.
* Тест `test_take_lead_race_concurrent_sessions` запускает 8 параллельных транзакций на PostgreSQL — победитель всегда один.
* Аналогично атомарны: одноразовые приглашения (`UPDATE invites … WHERE used_at IS NULL`) и ежедневная рассылка
  (`claim_once` — повторный запуск scheduler/cron в тот же день ничего не отправит).

## 11. Сделки

Мастер из 8 шагов (см. FSM). После подтверждения в одной транзакции: запись `deals`, объект → `sold`/`rented`
(для «другое» статус не меняется), связанная заявка → `closed`, записи в истории; затем commit и побочные эффекты:
снятие публикации (по настройке), карточка в «Архив», поздравление в теме «Сделки» (без суммы сделки),
уведомление владельцу. Владелец может изменить сумму/комиссию/дату/комментарий или отменить сделку
(с возвратом объекта в работу или без) — статистика пересчитывается автоматически, т.к. считает только `confirmed`.

## 12. Ежедневные отчеты

* APScheduler (часовой пояс `TIMEZONE`) в `REPORT_TIME` (по умолчанию 22:00, меняется в ⚙️) рассылает активным
  риелторам «Время ежедневного отчета…» с кнопкой «📝 Заполнить отчет». Через 90 минут владельцу приходит сводка
  с «❌ Отчет не предоставлен».
* Дублирующие HTTP-эндпоинты `POST /cron/report-reminders` и `/cron/report-summary` (заголовок `X-Cron-Secret`)
  для внешнего планировщика; идемпотентность обеспечивает `claim_once`.
* Отчет после полуночи (до 05:00) относится к предыдущему дню. Повторная отправка заменяет отчет за день.

## 13. Надежность и безопасность

* Webhook с `secret_token` (запросы без заголовка → 401). Polling — только для локального запуска.
* `safe_call` оборачивает вызовы Bot API: flood-control (retry_after), сетевые ошибки (повтор), остальные — лог без падения.
* БД: `pool_pre_ping`, ожидание доступности при старте, в middleware — rollback и сообщение «База данных временно недоступна».
* Логи не содержат телефонов/имен клиентов (только коды заявок и маскированный телефон), логгеры aiogram/SQL/httpx приглушены.
